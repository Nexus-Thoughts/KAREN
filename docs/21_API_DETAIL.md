# 21 — API Contract Detail

`docs/11_API_CONTRACT.md` lists endpoint groups with no method/schema detail
(docs/00 §12). This document supplies that detail and is updated as each
phase adds surface. KAREN's "API" is deliberately two layers, not one:

1. **PostgREST**, auto-generated by Supabase directly from the schema and
   RLS policies in `supabase/migrations/`. Every table and RPC function
   granted to `authenticated` is reachable at
   `${SUPABASE_URL}/rest/v1/<table>` and `${SUPABASE_URL}/rest/v1/rpc/<fn>`.
   Authorization is enforced by RLS, not by hand-written endpoint code — so
   "the API contract" for table access *is* `docs/20_DB_SCHEMA_DETAIL.md`'s
   RLS column, and this document does not repeat it per-table.
2. **Edge Functions**, for anything requiring secrets or server-side-only
   logic that RLS cannot express (KAREN, document generation, geofence event
   processing) — see `docs/02_SYSTEM_ARCHITECTURE.md`. Documented individually
   here as they land.

Every endpoint in both layers requires a valid Supabase session (bearer
JWT). There is no unauthenticated surface except `/auth/*` itself, which
Supabase Auth owns.

---

## RPC surface (PostgREST, Phase 4)

### `POST /rest/v1/rpc/my_profile`

| | |
|---|---|
| Auth | required (any active session) |
| Authorization | none beyond authentication — a caller may always read their own profile |
| Request | `{}` (no arguments) |
| Response | `SessionProfile` (see `src/types/domain.ts`): `{ user_id, email, full_name, status, student_id, faculty_id, roles: RoleAssignment[], permissions: string[] }` |
| Errors | `401` no session; PostgREST default error shape otherwise |
| DB entities touched | `users`, `user_roles`, `roles`, `role_permissions`, `permissions`, `students`, `faculty` (all read-only, via `SECURITY DEFINER`) |
| Audit | not audited — a read of one's own profile is not privileged |
| Notes | Single round-trip session bootstrap. Called once by `AuthProvider` on sign-in and on every `onAuthStateChange`. |

### `POST /rest/v1/rpc/my_permissions`

| | |
|---|---|
| Auth | required |
| Authorization | none beyond authentication |
| Request | `{}` |
| Response | array of `{ permission_key, resource, action, is_sensitive }` |
| Errors | `401` no session |
| Notes | UI-affordance convenience only (docs/13: "frontend hiding is not security"). Subsumed by `my_profile()` in practice; kept as a standalone RPC because KAREN's permission-guard layer (Phase 15) calls it directly without needing the rest of the profile payload. |

## Table surface (PostgREST, Phase 4)

Every table below is reachable at `/rest/v1/<table>` with standard
PostgREST query semantics (`select`, `eq`, embedding via foreign keys, etc.).
Method availability and row visibility are exactly what
`docs/20_DB_SCHEMA_DETAIL.md`'s RLS section states per table — restated here
only as a method matrix so the two documents don't fall out of sync on
substance, only on which one has the prose.

| Table | GET | POST | PATCH | DELETE | Scope predicate (see docs/20 for detail) |
|---|---|---|---|---|---|
| users | ✓ (self / in-scope) | via `users.write` only | self or `users.write` | via `users.write` only | department/student reach |
| roles, permissions | ✓ (any active user) | — | — | — | migration-owned |
| role_permissions | ✓ | `permissions.manage` | `permissions.manage` | `permissions.manage` | — |
| user_roles | ✓ (self / in-scope) | `roles.assign` + scope | `roles.assign` + scope | — (revoke via PATCH status) | department |
| departments | ✓ (any active user) | `departments.write` | `departments.write` | `departments.write` | global |
| courses | ✓ | `courses.write` + scope | same | same | department |
| academic_years, semesters | ✓ | `academic_terms.write` | same | same | global |
| sections | ✓ (scoped or structural) | `sections.write` + scope | same | same | department |
| faculty | ✓ (self / scoped / student-visible) | `faculty.write` + scope | same | same | department |
| students | ✓ (self / scoped) | `students.write` + scope | scoped, dept-checked | — (deactivate via PATCH status) | student/department |
| subjects | ✓ | `subjects.write` + scope | same | same | department |
| faculty_subject_assignments | ✓ (own / section) | `faculty.write` + scope | same | same | department (via section) |
| student_subject_enrolments | ✓ (own / scoped) | `students.write` (via `can_write_student`) | same | same | student |
| audit_logs | ✓ (`audit.read`, scoped) | — | — | — | append-only, no client write path at all |

Every `POST`/`PATCH`/`DELETE` above additionally fires the table's
`cims.audit_row_change()` trigger — the mutation is captured in
`audit_logs` regardless of which layer (PostgREST, Edge Function, or a
future admin tool) performed it, because the trigger runs at the database,
not in application code.

**Validation.** Column constraints (`check`, `unique`, `not null`, enum
types) are the first validation layer and reject malformed writes with a
Postgres error PostgREST surfaces as `400`/`409`. Request-shape validation
(zod schemas) is added at the Edge Function layer starting Phase 14 for
KAREN tool arguments; plain CRUD through PostgREST relies on the database
constraints, which is why `docs/20` documents every `check` constraint
explicitly rather than leaving shape validation implicit.

## Auth (Supabase Auth, Phase 4)

| Endpoint | Method | Notes |
|---|---|---|
| `/auth/v1/token?grant_type=password` | POST | Email + password sign-in. `signup` is disabled at the project level (`supabase/config.toml`: `enable_signup = false`) — accounts are provisioned by an administrator via `users.write`, never self-registered, per docs/04 least-privilege. |
| `/auth/v1/logout` | POST | Session invalidation. |
| `/auth/v1/user` | GET/PUT | Profile self-service (email/password change) — subject to Supabase Auth's own re-auth requirements, unrelated to the `public.users` RLS above. |

No KAREN code implements authentication; it is entirely GoTrue (Supabase
Auth), configured in `supabase/config.toml`.

## Rate limiting

Not yet implemented. Supabase's platform-level rate limits apply to the
local/hosted PostgREST and Auth endpoints as a baseline. Per-user rate
limiting for the KAREN conversation API (`KAREN_RATE_LIMIT_PER_MINUTE` in
`.env.example`) is enforced inside the `karen-chat` Edge Function starting
Phase 14, per docs/44.
